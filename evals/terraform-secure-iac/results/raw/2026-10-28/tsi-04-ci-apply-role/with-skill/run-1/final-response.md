I added the GitHub OIDC provider and two IAM roles, but I couldn't run `terraform validate`, `tflint` or a plan. Nothing is committed.

**What I added**
- **`ci.tf`:**
  - **OIDC provider:** the GitHub Actions provider, with audience `sts.amazonaws.com`.
  - **`ingest-ci-plan`:** read-only on the three resources, plus read on the state object and the `.tflock` object that `use_lockfile` writes. A pull request can assume it, and only through the exact subject `repo:platform/ingest:pull_request`.
  - **`ingest-ci-apply`:** named write actions on the landing bucket, queue and table, plus access to this configuration's state key. Only the exact subject `repo:platform/ingest:ref:refs/heads/main` can assume it.
  - **Session length:** both roles are capped at one hour.
- **`variables.tf`:** the repository, apply branch, state bucket and state key. The defaults match the existing backend block and `platform/ingest`.
- **`.gitignore`:** state, plan and tfvars patterns. There wasn't one before.
- **`.terraform.lock.hcl`:** generated by `init`.

**Design choices**
- **Separate plan and apply roles:** a pull-request run can't write to anything. Using one role for both would have let a pull-request workflow write to the managed resources.
- **IAM is read-only for the apply role:** it can refresh the CI roles but not change them, so a merged change can't widen the role that applies it. Changes to `ci.tf` have to be applied by an administrator. You may want a different split.
- **No wildcard actions or resources:** the only `*` resources are none. Prefix wildcards such as `s3:GetBucket*` appear on read paths only.
- **No credentials in the repo:** it holds no keys or account IDs. The account ID is never written out, so the data source `aws_caller_identity.current` is declared but not used anywhere.

**Not verified**
- **`terraform fmt -check`:** clean.
- **`terraform init -backend=false`:** succeeded.
- **`terraform validate`:** failed. The AWS provider plugin wouldn't start in this sandbox ("Failed to read any lines from plugin's stdout"). I didn't retry outside the sandbox, so the configuration is checked statically only.
- **`tflint` and scanners:** not installed here, and the repo configures none.
- **Plan:** not run, because there are no credentials or backend access.
- **Lock file:** `terraform providers lock` for linux and darwin on amd64 and arm64 failed with "disk quota exceeded". The lock file only has this host's checksum. Please run `terraform providers lock -platform=…` for the platforms CI and developers use.

**Before you apply**
- **Existing OIDC provider:** an AWS account can hold only one provider per issuer URL. If this account already has the GitHub one, run `terraform import` on it rather than creating it.
- **Bootstrap apply:** this has to be run by an administrator, since CI can't create its own roles.
- **State permissions:** the state policies assume the S3 backend with `use_lockfile`. If the state bucket uses a customer-managed KMS key, both roles also need `kms:Decrypt` and `kms:GenerateDataKey` on that key.
- **Workflow side:** the workflow needs `permissions: id-token: write` and `contents: read`, and `aws-actions/configure-aws-credentials` pinned by commit SHA, with the plan or apply role ARN. Run `apply` only on `main` and consider a protected environment. If you add one, the subject becomes `repo:…:environment:<name>`, so the trust condition must change to match.
