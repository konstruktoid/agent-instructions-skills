  **Publication and authors**
  - Published March 8, 2023. Author: Billy Lynch, Staff Software Engineer (Chainguard).
  - Disclosure: found September 7, 2022; reported to GitHub via the GitHub Bug Bounty program on September 8, 2022. Published 180 days after disclosure, following HackerOne's disclosure guidelines.
  
  **Background on fork networks**
  - Forks are created quickly because GitHub shares Git objects between a fork and its parent. The post links to GitHub's "counting objects" blog post and says this works through Git alternates.
  - GitHub lets users check out pull requests from forks via the parent repo. The authors say this "can be extended to fetch arbitrary commits from forked repositories, even those not directly associated with a pull request."
  
  **Mechanism of imposter commits**
  - The authors define them as: "Imposter commits are commits that appear to be from a parent repository, but they actually belong to a fork."
  - Because of how GitHub treats forked commits, Git or GitHub's API can fetch them from the parent repo, and this is often not obvious.
  - Prior incident cited: a 2020 commit in github/dmca impersonating then-CEO Nat Friedman, which GitHub confirmed was not a compromise. GitHub now recommends signed commits and shows a UI warning for commits not on a parent-repo branch. The post says no similar protection exists in the CLI or the API.
  
  **CI/CD impact**
  - Using a commit SHA from a fork in a workflow (for example, actions/checkout pinned to a fork commit) makes GitHub Actions fetch that SHA "regardless of whether it is reachable from a branch in the parent repository."
  - Because the action is referenced through the parent repo's name, Actions treats it as belonging to the parent. The post says this "can bypass GitHub Actions security settings that would normally restrict Actions to trusted sources."
  - The authors classify it as a form of dependency confusion. Exploitation needs a workflow author to use a SHA from an unpublished version and a maintainer to accept the change, likely via social engineering or careless review.
  
  **Exact examples and commands**
  - The page's workflow YAML, Git/API commands, and screenshots are not present in the extracted text, so I cannot quote them. The post refers to an example workflow using actions/checkout pinned to a fork commit (linked as github.com/actions/checkout/commit/c7d749a2d57b4b375d1ebcd17cfbfb60c676f18e).
  
  **Detection and tools**
  - Tool: clank, open-sourced by Chainguard at github.com/chainguard-dev/clank, to check a user's own workflows for imposter commits. The exact invocation is not in the extracted text.
  - Planned: a similar check for OpenSSF Scorecards, described as "soon."
  - Recommended: audit CI configs for jobs that could fetch arbitrary imposter commits, especially deployment and artifact-signing workflows.
  
  **Mitigations recommended**
  - Keep actions up to date with Dependabot against known branches and tags.
  - Pin dependencies, which the post calls good practice, but notes that a pinned SHA can still be an imposter commit.
  - Code signing: the authors say it "depends." Commits would need a repository-specific identity, and any human with that identity could sign in a fork. GitHub's web-flow.gpg key makes this hard to rely on in practice. They suggest per-repo signed release tags from trusted releasers, using Sigstore's Gitsign.
  
  **GitHub's response**
  - GitHub updated its docs on using SHAs with third-party actions (security hardening guide and "finding and customizing actions" pages).
  - GitHub removed short-SHA references for actions (changelog dated 2021-01-21), which the authors say makes SHA-collision abuse less likely.
  - GitHub is working on improvements to Actions publishing (github/roadmap issue 592). The post does not say the imposter-commit behavior itself was changed.
  
  **Limitations stated**
  - "we are not aware of any active exploitation, though we have not done an exhaustive search of public repositories."
  - The authors frame it as "an intentional (though perhaps unexpected) property of GitHub repositories," with the Actions bypass as the bug.
  - Code signing is not a complete answer, as noted above.

  (1) Locked commit must be on a branch? Yes, in the action's own repository. Docs: "This commit must be reachable from the branch or tag recorded for it in the lockfile, in the action's own repository. A commit that exists only in a fork, or that's no longer reachable from that branch or tag, is rejected when the workflow runs." So it is verified at run time, not only at generation. Generation also reports drift: a moved branch or partial ref gives a `ref-moved` warning, and `--verify` fails on a stale lockfile.
  
  (2) Coverage:
  - Reusable workflows: NOT covered. Docs: the lockfile "doesn't pin calls to reusable workflows (`jobs.<job_id>.uses`)"; reference them by full commit SHA instead. Their dependencies are covered by the lockfile of the repository where they are defined.
  - Local actions: partly. The extension "never follows or locks a local path action (`uses: ./…`)". A `$/` path is pinned and its dependencies can be locked. `gh actions-lock --migrate-local-actions` rewrites `./` to `$/`. With `--ignore-local-actions`, a `./` action that uses unlocked actions fails at run time with an error such as "lockfile missing pin for ...".
  - Docker actions: not mentioned on any page I read. Unknown from my sources.
  
  (3) Run-time enforcement: Yes. "The locked commit is what runs when the workflow executes." After onboarding, "Every action dependency the workflow uses must be present in the lockfile." On mismatch (commit not reachable from the recorded ref), the run is rejected. `owner_id`/`repo_id` are also checked at run time. For a workflow not onboarded: with the Require lockfile policy Active it is blocked ("blocks runs of targeted workflows that aren't onboarded"). Without the policy the docs do not say explicitly; the gradual-onboarding wording implies it runs as before.
  
  (4) Generate and enforce:
  - Install: `gh extension install github/gh-actions-lock`
  - Generate: `gh actions-lock` (all workflows) or `gh actions-lock .github/workflows/ci.yml` (one). Review the full diff, since it also rewrites uses refs (e.g. @v3 to @v3.1.0).
  - Keep current: Dependabot regenerates entries only for already-onboarded workflows. CI can run `gh actions-lock --verify` as a required check.
  - Enforce: set the Require lockfile policy to Active, at enterprise, organization, or repository level. Pilot first in Evaluate mode, which the enforce page says is "only available on GitHub Enterprise Cloud."
  - Allowlists: once onboarded, checks use locked SHAs, so tag entries such as actions/checkout@v6 no longer match. Use a wildcard or full SHA.
